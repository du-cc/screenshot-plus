# Screenshot Plus

> [!NOTE]
>
> This docs is generated by AI. Mostly technical.

GNOME 50's own screenshot and screen-recording tool, with ShareX-style files
and the options GNOME doesn't have. The keys are unchanged: Print opens the
tool, Shift+Print takes the whole screen, Alt+Print takes the focused window,
and Ctrl+Shift+Alt+R starts or stops a recording.

## Files

- Folder: `~/Pictures/Screenshots` by default. Recordings go to the same
  folder unless you set another one.
- Subfolder pattern: `%y-%mo`, which gives `2026-10/`.
- Name patterns: `%ra{10}`, or `%pn_%ra{10}` when the app is known. So you
  get `brave_x8Kd02LmQx.png`, as in ShareX.
- The app is the window you picked (window mode), the window under the middle
  of the area (area mode), or the focused window (screen mode and Shift+Print).
- Tokens are listed in Preferences → Files → Pattern tokens.
- Tidy up → Sort… moves loose files from the top folder into month folders,
  renamed with the pattern, and Undo puts them back. The undo list is
  `~/.local/state/screenshot-plus/last-tidy.json`.

## Screenshots

- Formats: PNG, JPEG, WebP or AVIF, with a quality setting.
- Size: full, logical (undoes display scaling, so 2880×1800 becomes
  2304×1440 at 125%), 75%, 50% or 25%.
- HDR: while a screen is in HDR mode, the screenshot tool shows the frozen
  screen in HDR (GNOME's own copy is SDR, so HDR content dimmed when it
  opened). With HDR screenshots on (off by default), area and full-screen
  shots are saved as:
  - AVIF with a gain map (default): the 10-bit BT.2020/PQ picture as the base,
    plus an ISO 21496-1 gain map down to GNOME's SDR picture. GNOME's Image
    Viewer (glycin) shows the base in HDR; gain-map viewers (Android
    galleries, iOS 18+, macOS 15+, Chrome) show it in HDR or SDR to suit the
    screen. Google Photos shows gain maps only on an SDR base, so it shows
    these SDR; use Ultra HDR JPEG for it. Needs ffmpeg.
  - Ultra HDR JPEG: GNOME's SDR picture plus a gain map up to HDR (Adobe/
    Google XMP and ISO 21496-1). Android 14+ phones and Chrome show it in
    HDR; GNOME's Image Viewer shows it SDR. Needs `gst-launch-1.0` with
    `jpegenc` (GStreamer good plugins).
  - 16-bit PNG in BT.2020/PQ: HDR in GNOME's Image Viewer, washed out
    elsewhere.
  The clipboard, window shots and the pointer stay SDR.

## Recording

- Formats: MP4 (H.264, HEVC or AV1) or WebM (VP9).
- Encoder: GPU (VA-API), CPU, or Automatic (GPU first).
- Frame rate (up to the screen's refresh rate), maximum height and bitrate
  are adjustable.
- HDR (off by default): while the screen is in HDR mode, records 10-bit
  BT.2020/PQ with VA-API H.265, AV1 or VP9. H.264 has no HDR, so it switches
  to H.265.
- Audio: desktop sound and/or microphone, as Opus.
- How it records: Screenshot Plus asks Mutter for the screen-cast stream itself
  and runs `gst-launch-1.0`, so frames go from the GPU straight into VA-API
  without a CPU copy. GNOME's recorder service can only take custom settings
  through a path that copies every frame to the CPU.
- Mutter's area streams are SDR and capped at 60 fps. Whole-monitor streams
  run at the refresh rate and, in HDR mode, also offer 10-bit PQ frames. So
  above 60 fps or for HDR it records the monitor and crops the area
  (`videocrop`, which VA-API applies on the GPU).
- The stock `pipewiresrc` (PipeWire 1.6.9) can't take those 10-bit frames.
  `lib/gst/libgstpipewirehdr.so` is the same element, built by
  `build/build-pipewirehdr.sh` as `pipewirehdrsrc`, with Mutter's
  `xRGB_210LE` mapped to `BGR10A2_LE`/`AR30` and the colour tags Mutter
  requires. It is used only for HDR, with its own plugin registry in
  `~/.cache/screenshot-plus/`. If it ever fails to load, recordings fall
  back to SDR.
- HDR is recorded only from DMA-BUF frames. For shared-memory (memfd) frames
  Mutter 50 paints 8-bit ARGB32 (PQ-encoded) into the buffer whatever format
  was agreed, so read as 10-bit they came out in nonsense colours. If the
  DMA-BUF pipeline fails, the recording is SDR.
- The VA encoders leave the bitstream's colour "unspecified"; only the
  container says BT.2020/PQ. Firefox reads the bitstream, so it played HDR
  recordings as SDR. When an HDR recording stops, ffmpeg copies it once with
  bitstream filters (`av1_metadata`, `hevc_metadata`, `vp9_metadata`) that
  write the colour into the stream, without re-encoding. The copy also sets
  the container's colour (`-color_primaries` etc.): ffmpeg otherwise takes it
  from the stream as it was before the filters, which dropped the MP4 `colr`
  box and tagged WebMs with the BT.709 matrix. HEVC is tagged `hvc1` for
  Apple devices. If ffmpeg is missing or fails, the file is kept as recorded.
- The 10-bit RGB frames are turned into YUV by `vapostproc`. On Intel (iHD
  driver) that runs in a shader whose matrix is rounded to 1/128ths, and for
  BT.2020 limited-range YUV greys came out green in proportion to their
  brightness. So once per session, before the first HDR recording,
  `lib/vpp-check.py` sends four known colours through vapostproc in each way
  the pipeline can convert, and the recorder uses the first that comes out
  right. In order:
  - `limited`: one pass, limited range; right on most drivers.
  - `twopass`: through limited-range RGB, which iHD rounds neutrally.
  - `full`: full-range YUV, tagged as such.
  - `cpu`: the GPU only copies, `videoconvert` does the maths.
  It never falls back to a conversion that measured wrong. The choice is
  logged (`journalctl --user -b -g "Screenshot Plus"`);
  `python3 lib/vpp-check.py -v` prints the measurements.
- While a selection or whole-screen recording runs, a round stop button
  floats next to the area (inside it for whole-screen recordings). It shows
  on screen but not in the recording: it is drawn into the screen's
  framebuffer after Mutter has taken the frame (`lib/stop-button.js`).
- HDR recordings run at a constant frame rate (`videorate`): Mutter only
  sends a frame when the screen changes, and YouTube processes HDR only at
  standard rates up to 60 fps. HDR10 mastering/MaxCLL metadata isn't written
  (Mutter doesn't know the monitor's real peak, and `webmmux` scales the
  luminance wrongly); YouTube then assumes its default mastering display.

## How the HDR capture works

GNOME draws screenshots in 8-bit sRGB. For HDR, the stage is drawn again into
a 16-bit float texture in the screen's own PQ colour state. GJS can't read
GPU memory directly, so a shader splits each 16-bit value into a high-byte
image and a low-byte image. Those come back through `Shell.Screenshot`, and
`lib/hdr-encode.py` joins them and writes the file (it uses ffmpeg for AVIF,
converting with `zscale`: FFmpeg 8's own `scale` turns neutral greys
slightly green).

For the gain maps it also gets GNOME's SDR picture and the screen's SDR white
level (`ref lum` of its colour state), compares the luminance of the two at
one spot per 2 x 2 block (a half-size map: an Android phone's own gallery
showed AVIF gain maps in HDR at 1/2 size, not at 1/3 or 1/4), and stores log2(HDR / SDR) as an 8-bit one-channel map,
which is what ISO 21496-1 wants whichever picture is the base. GNOME's SDR
picture tone-maps highlights rather than clipping them, so the range comes
from the measured ratios; the pointer (only in the SDR picture) can't stretch
it. The AVIF is assembled by hand from two ffmpeg/libaom stills, in the same
layout as libavif (base as primary item, a `tmap` item preferred through an
`altr` group, the gain map hidden), so no other tool is needed. Both JPEGs
are 4:4:4 from `jpegenc`.

## Files in this folder

| File | Role |
|---|---|
| `extension.js` | hooks into GNOME's screenshot UI and the two shortcuts |
| `lib/capture.js` | saving screenshots: format, size, HDR, clipboard, notification |
| `lib/recorder.js` | recording: Mutter screen-cast and gst-launch pipelines with fallbacks |
| `lib/naming.js` | patterns, folders, tidy-up (also used by prefs) |
| `lib/hdr-encode.py` | joins the HDR halves into a PNG with a cICP chunk, a PQ AVIF with a gain map, or an Ultra HDR JPEG |
| `lib/vpp-check.py` | measures which GPU conversion to 10-bit YUV keeps colours right (HDR recording) |
| `lib/stop-button.js` | the floating stop button that recordings don't show |
| `lib/gst/libgstpipewirehdr.so` | `pipewirehdrsrc`, for 10-bit HDR screen-cast frames (rebuild after a PipeWire major update) |
| `prefs.js` | preferences window |
